# 测试与回归规范（tester subagent 必读）

本文件是 `dev-rule` skill §五「测试与交付」的详细规范，**仅在以下情况读取，不常驻上下文**：

- 被调度为 tester subagent 时：执行测试前必须完整读取本文件，它是你的行为约束。
- main agent 进入测试阶段、需要核对测试规范时。

来源：dev-rule SKILL.md §五。

---

## 5.1 测试策略

- **单元测试**：核心函数/类的输入输出与边界。
- **集成测试**：模块间接口与数据流是否通畅。
- **边界与回归**：空值、越界、并发、超时；改动是否破坏既有功能。
- 至少运行语法检查或测试（按 `references/coding-standards.md` §4.7 工具链），不可跳过。

## 5.3 测试脚本规范

函数级测试与复杂场景测试统一固化到项目 `tests/`，不要只写在对话里跑一次就丢--不固化的测试无法回归，下次改动就没人再跑它。

- **函数级测试**：为核心函数/类编写输入输出与边界用例，放 `tests/test_<模块>.py`。
- **复杂场景测试**：多模块协作、完整调用链、集成场景放 `tests/test_<场景>.py`。
- **仅一次性验证**（临时确认某个猜想）可 inline 跑，但不固化、不作为回归依据。
- **可运行**：测试须能直接 `pytest tests/`（或项目对应工具）跑通，不得只写不跑。

## 5.4 逻辑 bug 固化与回归

用户报告的逻辑 bug 是高价值信号，修完不算完--必须留下回归防线，防止后续改动把它重新引入。

- **编回归测试**：为该 bug 编写复现用例，放 `tests/`，断言修复后的预期行为。
- **固化到文档**：在项目 `docs/bugs/` 目录下按类别归档记录，**每个 bug 一个文件**，不使用单一文件堆积（原 `docs/bug-regression.md` 弃用）：
  - 目录结构：`docs/bugs/<类别>/<bug 名>.md`。示例：`docs/bugs/logic/order-refund-double.md`。
  - `<类别>` 语义化归类，如 `logic`/`api`/`data`/`concurrency`/`perf`/`ui` 等，可扩展；同类别 bug 归入同一子目录。
  - 每个 bug 文件固定记录：`现象` / `根因` / `修复` / `回归用例位置` / `关联`（可关联到调用链或相关 bug）。
  - 若 `docs/bugs/` 不存在则新建（含 `README.md`）；项目已有 `docs/bugs/README.md` 时，在该索引表中登记本次 bug 的（类别/名称/回归用例/状态）。
- **每次修改后回归**：改动相关代码后必须跑相关回归测试，确认未重新触发已记录的 bug。回归失败必须报告，不得静默放过。
