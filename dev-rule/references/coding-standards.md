# 编码实现规范（coder subagent 必读）

本文件是 `dev-rule` skill §四「编码实现」的详细规范，**仅在以下情况读取，不常驻上下文**：

- 被调度为 coder subagent 时：执行编码前必须完整读取本文件，它是你的行为约束。
- main agent 进入编码阶段、需要核对某条编码规范时。

来源：dev-rule SKILL.md §四。

---

## 4.1 调用链溯源与全局视角

**不局限于当前代码或函数的上下文窗口。** 生成方案时必须沿调用链和数据流完整溯源，从全局和输入输出两端定位 bug 来源与真实修改点。

- **沿调用关系追溯**：谁调用当前函数、当前函数调用谁；报错点未必是根因点，根因常在上游传参、数据生成或下游消费处。
- **从 IO 两端看数据流**：输入来源、经过的变换、在哪一步被污染、输出去向。从两端向中间收敛定位。
- **验证数据语义**：调用链不止追"谁传给谁"，必须在每一跳验证"传的数据对不对"--字段职责是否混用？格式是否匹配消费方预期？上游产出数据在语义上是否正确？只追调用关系不验数据语义等于没追。
- **最小改动约束修改范围，不约束观察范围**：可以广度扫描调用链上所有相关代码，但只修改任务边界内的代码。发现范围外问题必须主动报告（见 §4.6）。
- **修改必须落在根因上**：修在根因而非症状处；报错点只是症状时，在报错点修等于掩盖问题。

## 4.2 正向与反向双向思考

生成方案时必须从正向和反向两条**独立逻辑路径**分别思考，交叉验证后输出。反向思考是独立路径，不是给正向方案挑刺。

**【正向思考】原因/输入 -> 结果/输出**
- 沿"代码做了什么 -> 应产生什么 -> 实际产生什么"推导
- 沿调用链正向走数据流，定位预期与实际的分叉点

**【反向思考】从结果/输出反推，或从对立假设出发**
- **根因追到底**：看到报错时，反向追溯不能停在"错误怎么传播"，必须追到"错误为什么发生"--从报错点倒推输入来源，验证输入语义正确性。修错误传播是治标，修错误根因是治本。
- 逆向追溯：从报错/异常倒推--"要产生这个结果，上游必须发生什么？"
- 对立假设：假设"问题不在当前怀疑点"，根因还会在哪？假设"这个修改反而是错的"，真正修复在哪？
- 否定式推理：这个 bug 在什么条件下**不会**出现？那些缺失的条件就是根因。
- 逆向数据流：从数据流终点回溯起点，定位数据在哪一步被污染。

**【交叉验证】**
- 正向与反向都指向同一修改点 -> 方案成立
- 两条路径结论冲突 -> 显式陈述分歧并先解决，不得只取正向
- 只有正向没有反向 -> 方案不完整
- 反向思考必须产出实质性推论，不能是"假设不是 X 就是 Y"的套话
- 简单任务可压缩深度，但至少要有一句反向确认

## 4.3 注释规范

只解释**为什么**，不解释**是什么**。代码本身已说明操作，注释补充业务逻辑、设计决策或技术妥协。

```
// ❌ 解释是什么（代码已说明）
i += 1

// ✅ 解释为什么
// 从 1 开始计数：ID 从 1 起，0 保留为占位符
i = 1
```

- 不为自解释代码（如 `len(users)`）加冗余注释。
- 核心模块和公共接口必须标注输入输出参数结构与含义：

```
function create_user(
    data: UserCreate,  // {username, email, role?}
) -> UserProfile      // {user_id, username, email, created_at}
    // 返回完整 Profile 而非仅 user_id：前端注册需立即展示头像昵称，省一次请求。
```

## 4.4 最小改动原则

- **精准修改**：只改与当前任务直接相关的文件和代码行，像外科手术。不顺手统一格式、重命名、重排函数。
- **尊重历史代码**：现有风格"不够优雅"但能正常工作且与任务无关时，不顺手重构。发现坏味道要主动报告或另行提问，不要静默忽略。
- **避免大面积格式化**：改几行不要触发整文件重格式化，以免干扰版本控制和审查。格式化单独开 PR。

## 4.5 文件修改方式规范（基于最新磁盘状态的最小 diff）

**磁盘上的文件是唯一真相，上下文里缓存的代码可能已经过期。** 上一轮对话结束后，用户可能手动改过代码，其他工具或队友可能提交过改动，长对话压缩也可能让上下文失真。基于过期的上下文代码去修改，要么改错位置，要么覆盖掉用户刚做的改动。因此每次落笔前，必须以磁盘最新内容为准。

- **禁止整文件重写**：局部修改不得用"写入整个文件"的方式完成，必须通过精确的字符串替换（diff/patch 式）只改动需要变动的片段。整文件重写会淹没真实改动、干扰版本审查，还可能用上下文里的旧内容覆盖掉磁盘上你没缓存到的最新代码。
  - 仅两种情况允许整文件写入：新建文件；或文件绝大部分内容确需重写（此时先向用户说明理由并确认）。
- **修改前必须重读目标文件**：即便是刚处理过的文件，执行修改前也要重新读取，确认两件事--(1) 修改位置的代码与你记忆中一致；(2) 你要替换的旧片段在文件中确实存在且唯一。重读的代价远低于改错位置后回滚。
- **发现不一致时以磁盘最新为准**：重读后若磁盘代码与上下文里记住的不同，说明用户手动改过或环境已变化。**以磁盘最新代码为准**，不得用上下文里的旧版本去"纠正"磁盘。先理解最新代码的意图，再在新代码上重新定位修改点；若最新改动与当前任务冲突，先向用户澄清而非擅自覆盖。
- **替换片段要足够具体**：用作匹配的旧字符串应带足够上下文以保证在文件中唯一，避免误匹配到其他相似片段。

## 4.6 范围外问题主动报告

**最小改动原则约束的是"改什么"，不是"看什么"。** 沿调用链溯源时若发现任务范围外但影响功能正确性的设计缺陷或 bug，必须主动向用户报告，不得沉默。

- **何时报告**：发现数据语义不匹配、字段职责混用、输入格式与消费方预期不符、缺失必要转换层等问题时，即使不在当前任务范围内也必须提示。
- **如何报告**：在方案末尾或回答中附加"⚠️ 范围外发现"段落，简述问题、影响和建议，由用户决定是否处理。
- **为什么必须报告**：用户委托你修一个环节，不代表只关心这一个环节。沉默会让用户以为系统没问题，直到问题暴露时已浪费大量时间。

## 4.7 工具链规范

项目使用统一约定的工具链，不得混用替代工具（用 `uv` 禁用 `pip`，用 `pnpm` 禁用 `npm` 等）。

| 操作 | 命令（Python/uv 示例） |
|------|------|
| 运行项目 | `uv run --no-sync python main.py` |
| 安装依赖 | `uv sync` |
| 添加新包 | `uv add <package-name>` |
| 语法检查 | `uv run --no-sync python -m py_compile <file>.py` |
| 运行测试 | `uv run --no-sync python -m pytest` |

> ⚠️ 运行项目必须带 `--no-sync`，否则可能覆盖锁定环境。

## 4.8 类型注解规范

强类型/支持类型注解的语言（Python / TypeScript / Rust / Go 等）必须遵守：

- **所有变量定义都要类型注解**，尤其是从字典/映射中取值时定义的变量。
  ```python
  # ❌ 无注解，dict 取值类型不明
  user = data["user"]
  # ✅ 明确类型
  user: UserDTO = data["user"]
  ```
- **禁止使用 `Any` / `any`**。类型不确定时用具体替代：
  - 字典结构已知 -> `TypedDict`（Python）或 `interface`/`type`（TS）定义字段类型，按字段取值后注解。
  - 结构未知/外部边界 -> 用 `object`、`Union`/`Optional`、泛型 `dict[str, X]`、`Protocol`，而非 `Any`。
  - 多种可能 -> `Union[A, B]`（Python）/ `A | B`（TS），不退化为 `Any`。
- **适用边界**：无原生类型系统的语言（纯 JS / Shell / 配置）不强制注解，可用 JSDoc 等等价手段或遵循该语言惯例，按 dev-rule §七 务实变通处理。

> ⚠️ `Any` 是类型系统的逃生舱，等于关闭类型检查；用 `Any` 的地方往往提示该补一个 `TypedDict`/`Protocol` 而非放弃。
